# ARCHITECTURE.md — Архитектура Decon

> Статус: v1.0, согласовано 2026-11-16. Изменения — только через PR с обновлением
> этого файла (правило №2 из CONVENTIONS.md).

## 1. Решения и их обоснование

| Решение | Выбор | Почему |
|---------|-------|--------|
| Язык | Rust (edition 2024) | Требование легковесности и контроль аллокаций; один язык на все таргеты |
| UI-фреймворк | Dioxus 0.7 | Один кодбазис: desktop сейчас, Android и web (WASM) позже, без переписывания UI. Перерисовка только по сигналу — низкий расход CPU в простое. Mobile-таргет пока сырой — учтено в ROADMAP (S6 не раньше стабилизации пилота) |
| Хранилище | SQLite (rusqlite), WAL | Один файл, ноль конфигов, транзакционность, платформонезависимость |
| Идентификаторы | UUID v7 | Временные, сортируемые, дружелюбные к будущей синхронизации клиента с сервером |
| Шифрование | fernet (AES-128-CBC + HMAC) для полей; ключ = argon2id(passphrase); хранение ключа в OS keyring | Требование №6: ноль конфигов + защита заметок. `keyring`-крейт: Secret Service (Linux), Wincred (Windows) |
| Тренажёры | Чистая логика без рендера, детерминизм по сиду | Headless-тесты и бенчмарки без UI; UI — тонкий слой поверх потока событий |
| Почему не Tauri | Tauri — рантайм над системным webview с JS-фронтендом; Dioxus — чистый Rust с тем же webview-рендером на десктопе, но с web/mobile-таргетами из коробки | Траектория «десктоп → Android → веб-сервис сообщества» — это ровно дорожная карта Dioxus; миграция между фреймворками = переписывание UI, поэтому решение зафиксировано окончательно |

Правило структуры (№7 из CONVENTIONS.md): модель — папка родственных модулей,
каждый модуль — отдельный файл с говорящим именем. `views/` отражает экраны
приложения 1:1.

## 3. Ключевой принцип: `decon-core` не знает про UI

- `decon-core` компилируется без Dioxus и без async-рантайма — это же ядро
  позже поднимается на сервере (axum) для веб-сервиса сообщества (S7):
  модель, валидация, аналитика не дублируются ни строчкой.
- `decon-trainers` зависит только от `decon-core` (нужны типы результатов).
- `decon-app` — единственный, кто зависит от Dioxus; вся логика — вызовы
  core/trainers, UI только отображает и отправляет события.

## 4. Поток данных сессии

```
Запуск сессии
  → pre-замер (2 слайдера: pre.noise, pre.openness)
  → таймер (равномерные фоновые сигналы, не колокол; интервалы — из настроек)
  → event-log: кнопки-маркеры пишут события с таймкодом (срыв в концентрацию,
    уход в семантику, вспышка ясности — настраиваемый набор)
  → стоп → post-замер (5 слайдеров: uniformity, background, depth, stability,
    dissolution) + опциональная заметка (шифруется fernet)
  → (через 30–60 мин, опционально) хвост: post.carryover
  → всё в одну транзакцию SQLite
```

Тренажёры пишут в ту же таблицу сессий (`session.kind = 'trainer'`) со своими
метриками в `trainer_log` — аналитика видит единый ряд данных.

## 5. Зонды дня при ненормированном дне

- Настройки (в БД, не в файлах): окно активности (например 09:00–23:00),
  количество зондов (3–5), минимальный интервал, пауза на выходные/отпуск.
- Резидентный режим (S2.5): приложение живёт в трее — иконка, меню
  «Открыть/Выход», закрытие окна = свернуть в трей, автозапуск с системой
  по желанию. Зонды срабатывают при скрытом окне: уведомление ОС + звук,
  окно не крадёт фокус (пользователь отвечает, когда откроет Decon или
  кликнет уведомление). Повтор-«будильник»: fired-зонд без ответа
  напоминает каждые `reminder_interval_min` минут (`last_reminder_at`).
  На Android (S6) — системный планировщик.
- Догоняющие зонды: пропущенный зонд остаётся доступным, ответ сохраняется
  с полем `delay_minutes`; аналитика умеет отделять свежие срезы от
  восстановленных.
- `probe_scheduler.rs` — детерминированный (seed) для property-based тестов:
  зонды всегда в окне, интервал всегда ≥ минимума.

### 5.1. Персистенс и graceful shutdown (S2.5)

Принцип: сбор данных = персистенс священен. Все контролируемые сценарии
завершения проходят через один путь — `App::finalize_running` (модель
`Session::finalize` со статусом):

- **SIGTERM/SIGINT** (Linux): signal-hook выставляет флаг, тикер
  UI-потока финализирует сессию (`end_status=interrupted`), флашит
  журнал, WAL-checkpoint, выход;
- **«Выход» из трея**: тот же путь финализации, затем exit;
- **ручное прерывание** («Прервать сессию» на экране практики):
  `end_status=aborted`, post-замер не предлагается — событие уже записано
  с таймкодом;
- **закрытие/скрытие окна во время сессии**: сессия продолжается (окно —
  пульт, процесс — демон), завершается кнопкой или шатдауном выше;
- **recovery при старте**: сессии с `ended_at IS NULL` (краш, SIGKILL,
  отключение питания) закрываются как `interrupted` с `duration_s` от
  `started_at` (`SessionRepo::finalize_dangling`).

Стрим-флаш: журнал живой сессии льётся в БД каждые 15 с (`FLUSH_INTERVAL_MS`),
не дожидаясь stop — при неконтролируемом краше теряется максимум 15 с
событий, а не вся сессия. Автоматизировать нельзя только SIGKILL/power-loss
— это честно зафиксировано; всё остальное контролируемо.

## 6. Шифрование и приватность

- Автоматический режим (по умолчанию): ключ генерируется при первом запуске,
  кладётся в OS keyring. Ноль действий пользователя.
- Парольный режим (опция): ключ = argon2id(passphrase); passphrase в БД не
  хранится ни в каком виде, только в keyring по явному согласию пользователя.
- Шифруются только чувствительные поля (заметки, свободный текст зондов);
  шкальные ответы и метрики тренажёров — открытым текстом (аналитике нужны
  SQL-запросы по ним без расшифровки).
- Экспорт CSV/JSON: заметки по умолчанию выгружаются расшифрованными только
  в явный файл по запросу пользователя.

## 7. Память и производительность (правило №1)

Целевые бюджеты (проверяются бенчмарками criterion, планы — в ROADMAP по скоупам):

| Hot path | Бюджет |
|----------|--------|
| Append события в event-log сессии | 0 аллокаций (фиксированный буфер, `SmallVec`), flush батчами в SQLite |
| Тик MOT-движка (60 Гц, N ≤ 32 объектов) | 0 аллокаций на тик: `soa`/фиксированные массивы, обновление на месте |
| Скоринг шкал, дельты | без аллокаций на вызов (`&mut [Score]` на месте) |
| Корреляции/тренды на 10k сессий | < 50 мс холодный проход, без промежуточных Vec |

UI не входит в бюджет hot paths (Dioxus сам управляет своим рендером), но
idle-режим: 0% CPU при отсутствии сигналов (перерисовка только по изменению
состояния) — проверяется интеграционным smoke-тестом.

## 8. Терминология (соответствие системе дКВ)

| Термин Decon | Смысл |
|--------------|-------|
| Слой (layer) | Модальность/уровень дКВ: зрительный, слуховой, витальный (телесный), семантический, полимодальный |
| Равномерность | «Равномерное распределение внимания по всему полю воспринимаемых стимулов» — базовое определение дКВ (Бахтияров) |
| Осознаваемый фон | Отличительный признак дКВ: фон «однородный, но сознательно воспринимаемый» (при КВ — не фиксируемый) |
| Растворение фигур | Потеря выделенности объектов, слияние с фоном (против агглютинации фигур при рассеивании) |
| Carryover | Остаточный фоновой эффект практики в повседневности (замер зонами и хвостом сессии) |
| Срыв | Рецентрация внимания: уход в объект, семантику или тело; фиксируется событием с таймкодом |

## 9. Ограничения пилота (зафиксировано честно)

1. ~~Зонды — только при запущенном приложении (десктоп); решается в S6.~~
   Снято в S2.5: резидентный режим с автозапуском — зонды работают, пока
   приложение живёт в трее. На Android (S6) — системный планировщик.
2. Мобильный таргет Dioxus сырой; S6 стартует после стабилизации десктопа и
   проверки состояния Dioxus mobile на тот момент.
3. Биометрия (HRV/EEG) отложена по отсутствию оборудования; модель данных
   имеет место под `measurement`-таблицы (S8+, если понадобится) — см. SPEC.
4. FFMQ-15 подключается внешним файлом, текст пунктов в код не включается
   (лицензионная гигиена).
5. Windows-уведомления ОС (toast): notify-rust 4.x не поддерживает Windows —
   в S2.5 на Windows зонды оповещаются звуком (winmm) + трей-меню; нативный
   toast — при первой Windows-сборке (проверка в S6-порте). SIGTERM на
   Windows не приходит GUI-процессу — graceful exit через трей.
6. Автозапуск через XDG/HKCU — per-user регистрация; portable-режим без
   автозапуска поддерживается по определению (файла просто нет).
