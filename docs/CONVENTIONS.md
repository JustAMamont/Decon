# CONVENTIONS.md — Правила разработки Decon

> Эти правила обязательны всегда. PR, нарушающий правило, не мержится —
> независимо от того, насколько срочная фича. Изменение самих правил —
> отдельный PR с обоснованием и обновлением этого файла.

## Чек-лист перед каждым PR

- [ ] **Память:** hot paths без новых аллокаций (подтверждено бенчем, если
      PR их касается)
- [ ] **Доки:** затронутые разделы ARCHITECTURE.md / SPEC-data-model.md /
      SCALES.md / ROADMAP.md обновлены в этом же PR
- [ ] **Тесты:** новые пути кода покрыты unit/integration; математика —
      property-based; бенчи не деградировали (CI сравнивает с main)
- [ ] **Скоуп:** PR целиком внутри одного скоупа ROADMAP (или это
      технический рефакторинг без изменения поведения)
- [ ] **Секреты:** новых секретов, токенов, приватных ключей в diff нет
      (gitleaks в CI — блокер)
- [ ] **GitHub:** локально зелёно (fmt + clippy + test + gitleaks) перед
      пушем; `git fetch` сделан, пуш — сразу за коммитом; в `main` — только
      проверенный код; CI дергается только на границе скоупа (правило №8)
- [ ] **Ноль конфигов:** не добавлен ни один пользовательский конфиг-файл;
      новые настройки — через таблицу `settings`
- [ ] **Живая проверка UI:** экраны, которые менялись в PR, проверяются
      запуском приложения (xvfb-скрипт в scripts/), не только тестами —
      паника в use_hook/рендере не ловится unit-тестами (урок S4,
      2026-11-17: «Encountered panic: Any { .. }» доходил до пилота)
- [ ] **Структура:** новые модули лежат в своих файлах, в правильных папках
      (`model/`, `db/`, `analysis/`, `schedule/`, `trainers/`, `views/`),
      имена говорят сами за себя
- [ ] **Ноль интерактива в практике:** экран сессии не содержит
      интерактивных элементов, кроме приглушённого управления завершением
      (правило №9; урок 2026-11-17: кнопки-маркеры дошли до пилота и
      противоречили самой методике дКВ)

---

## Правило 1 — Легковесность и память

**Формулировка владельца проекта:** максимальная легковесность достигается
эффективной работой с памятью (минимизация аллокаций, отказ от
перевыделений — голый borrow checker, параллелизация, асинхронные мувы),
доказывается цифрами бенчмарков и тестами, включая интеграционные.

Операционализация в Decon:

1. **Бюджеты аллокаций задекларированы и проверяются** (ARCHITECTURE.md §7):
   - append события сессии — 0 аллокаций;
   - тик любого тренажёра — 0 аллокаций;
   - скоринг/дельты — 0 аллокаций на вызов.
   Бенчмарки criterion считают аллокации (подсчёт через
   `#[global_allocator]`-обёртку в тестовом профиле) и падают при превышении
   бюджета.
2. **Приёмы:** заимствования вместо клонов; `&mut [T]`-слайсы на месте
   вместо возврата `Vec`; `SmallVec`/`ArrayVec` для событий фиксированного
   размера; SoA-раскладка для объектов MOT; батч-запись в SQLite вместо
   построчной; переиспользование буферов между кадрами.
3. **Параллелизация/асинхронность уместно, не везде:** UI-поток — Dioxus;
   запись в БД и экспорт — отдельные потоки (`std::thread`, канал команд);
   async-рантайм не тянем в `decon-core` вообще — core синхронный и
   тестируемый как библиотека.
4. **Идти против правила можно только с цифрами:** «проще склонировать» —
   не аргумент; либо бенч, доказывающий несущественность, либо рефакторинг.
5. **Паники/ошибки:** `unwrap()` только в тестах; в продакшн-коде —
   `Result` с типизированными ошибками (`thiserror`), `expect()` — с
   сообщением, объясняющим инвариант.

## Правило 2 — Документация

1. Документация — часть кода, не приложение к нему: PR, меняющий поведение,
   меняет и доки в том же коммите.
2. `#![deny(missing_docs)]` на публичных API всех крейтов; rustdoc-комментарии
   объясняют «почему», а не пересказывают сигнатуру.
3. Living-документы: ARCHITECTURE.md (решения), SPEC-data-model.md (схема,
   версия = номер последней миграции), SCALES.md (набор шкал и версии),
   ROADMAP.md (статусы скоупов). Устаревшая документация хуже отсутствующей:
   найденное противоречие — баг, фиксится немедленно.
4. Решения, отклонённые по ходу (например, Tauri), фиксируются с обоснованием
   в ARCHITECTURE.md §1 — чтобы не возвращаться к ним без новых данных.

## Правило 3 — Тесты и бенчмарки обязательны

1. **Unit:** каждая публичная функция core/trainers; граничные случаи
   обязательны (пустой ряд, одно значение, деление на ноль в статистике).
2. **Integration (`tests/`):** сценарии через публичный API крейтов —
   полный цикл сессии, миграции up/down, roundtrip экспорта, детерминизм
   планировщика и тренажёров по сиду.
3. **Property-based (proptest):** вся математика аналитики — корреляции,
   тренды, n-of-1 статистика; генераторы синтетических рядов с известными
   свойствами.
4. **Бенчмарки (criterion):** в CI — smoke-режим (быстрая проверка, что не
   деградировали); полный запуск — локально перед мержем PR, задевающего
   hot paths. Результаты сравниваются с main; регрессия > 10% в hot path —
   блокер.
5. **UX-тесты:** интерактивные сценарии (пройти Шульте без ошибок, ответить
   на догоняющий зонд) — headless-прогоны на уровне core/viewmodel, без
   реального рендера.
6. Покрытие — инструмент поиска дыр, не KPI: `cargo llvm-cov` периодически;
   пустых тестов ради процента не пишем.

## Правило 4 — Скоупы в ROADMAP.md

1. Один PR — один скоуп (или внутренний рефакторинг без изменения
   поведения).
2. Переход к следующему скоупу — только после всех критериев приёмки
   текущего; статусы в ROADMAP.md обновляются в PR закрытия скоупа.
3. Критерии приёмки формулируются проверяемо (число, тест, зелёный CI),
   «работает» — не критерий.

## Правило 5 — Секреты

1. В репозитории не должно быть секретов: токенов, ключей, паролей,
   приватных сертификатов, личных данных.
2. gitleaks-скан — обязательная джоба CI, блокер мержа.
3. `.gitignore` закрывает `.env*`, `*.pem`, `*.key`, локальные базы
   (`*.db`, `*.sqlite*`), артефакты сборки.
4. Если секрет всё же попал в историю: немедленная ротация секрета + PR с
   переписыванием истории (владелец репозитория), а не «просто удалить файл».
5. Decon — локальное приложение: на этапах S0–S6 секретов в рантайме нет
   (ключ шифрования — в OS keyring пользователя, не в репо). Появятся —
   при S7 — все серверные секреты только через secrets CI/GitHub Actions
   и переменные окружения.

## Правило 6 — Ноль конфигурационных файлов

1. Пользовательских конфиг-файлов нет: ни TOML, ни YAML, ни JSON вне БД.
   Единственный файл пользователя — сама база SQLite в каталоге данных
   приложения: портабельный `data/` рядом с исполняемым файлом (с
   2026-11-17; старые базы из XDG_DATA_HOME/`%APPDATA%` переносятся в
   `data/` автоматически, исходник прячется в `decon.db.migrated`);
   fallback при неопределимом exe-пути — XDG_DATA_HOME на Linux,
   %APPDATA% на Windows.
2. Все параметры — таблица `settings` (ключ → JSON-значение), редактирование
   — экран настроек в UI.
3. `Cargo.toml`, `rust-toolchain.toml`, `.github/` — файлы разработчика,
   не пользователя; правило на них не распространяется.
4. Обновление приложения само применяет миграции; пользователь никогда не
   правит схему руками (SPEC-data-model.md §6).

## Правило 7 — Структура кода

1. Workspace = 3 крейта с жёсткой направленностью зависимостей:
   `decon-app → decon-trainers → decon-core`. Обратных и боковых связей нет.
2. Модель — папка родственных модулей; модуль — один файл; имя файла —
   имя модуля — смысл (`session.rs`, `probe_scheduler.rs`).
   Файл больше ~400 строк — повод поделить по смыслу.
3. Никаких «utils.rs»: вспомогательная функция живёт в модуле, которому
   принадлежит по смыслу; общий код для трёх мест — своя папка/модуль с
   именем этой ответственности.
4. UI (`decon-app`) тонкий: экран в `views/` не содержит логики, только
   вызовы core/trainers и отображение; state — в `state/`, платформенные
   вещи — в `platform/`.
5. Стиль: `rustfmt` без ручных отступлений (CI проверяет), clippy
   `-D warnings` — ноль предупреждений.
6. Коммиты: императив, что+почему (`db: батч-вставка событий — убрать
   аллокацию на строку`), размер — атомарныйreviewable шаг.

## Правило 8 — GitHub: коммиты, пуши, синхронизация

**Требование владельца:** своевременные коммиты и пуши; локальное и удалённое
состояния репозитория синхронизированы; на удалённый не должен попадать
устаревший или поломанный код.

Операционализация в Decon:

1. **Remote всегда зелёный.** Пуш в `main` допустим только после локальной
   проверки: `cargo fmt --check` + `cargo clippy --all-targets -- -D warnings`
   + `cargo test --workspace` проходят, приложение собирается. Пуш «сначала
   посмотрю CI, потом починю» запрещён.
2. **Атомарные коммиты, своевременные пуши.** Каждый завершённый смысловой
   шаг (скоуп или его самостоятельная часть) — отдельный коммит
   `что: почему`; пуш сразу после коммита, а не накоплением к вечеру.
   Прерывание работы = коммит WIP в ветку, не в `main`.
3. **Синхронизация перед началом работы.** Перед новым коммитом:
   `git fetch origin`, при расхождении — сначала `pull --rebase`, потом
   работа. Не работать поверх несинхронизированной копии и не пушить
   «вслепую», не сделав fetch.
4. **Не форс-пушить main.** `git push --force` в `main` запрещён. Переписывание
   истории — только в личных ветках и только при необходимости (правило №5.4:
   после утечки секрета).
5. **Ветвление для нетривиального.** Прямые коммиты в `main` — для атомарных
   шагов одного разработчика (текущий режим проекта). Как только вкладчиков
   больше одного, любая фича/фикс идёт веткой `feat/…` / `fix/…` → PR → CI
   зелёный → merge. Скоуп целиком закрывается merge-коммитом PR.
6. **Issues.** Баги и задачи — в GitHub Issues с меткой скоупа (`S1`, `S2`, …);
   коммит закрывает issue формулой `Closes #N` в описании. Issue без
   критерия проверяемости не заводится.
7. **Секреты и доступы.** Токены доступа — только через переменные окружения
   или локальный credential helper, никогда в файлах репозитория, CLI-истории
   и логах. `.env*` — в `.gitignore` с S0. Утечка = ротация немедленно
   (правило №5.4). Перед каждым пушем — локальный `gitleaks detect` по
   истории (замена CI-скану, см. п. 9).
8. **Релизы.** Тег `vX.Y.Z` (semver) — только из точки, где CI зелёный на
   обоих таргетах; тег пушится вместе с запуском release-workflow. Никаких
   тегов поверх непроверенного кода.
9. **Экономия Actions (бесплатный тариф).** CI не запускается на обычные
   пуши и PR — только на границах скоупов: вручную (workflow_dispatch) или
   тегом `scope-S<N>`. Внутри скоупа разработчик гоняет полный набор
   локально (fmt, clippy, test, bench smoke, gitleaks — эквивалент CI).
   Запуск CI на границе скоупа обязателен и должен быть зелёным до перехода
   к следующему скоупу. Лишние перезапуски, матрицы «на всякий случай» и
   experimental-раннеры запрещены.

## Правило 9 — Практика дКВ неприкосновенна: ноль интерактива

**Формулировка владельца проекта:** любые интерактивные элементы во время
практики разрушают измеряемое состояние; предложение «кликать во время
деконцентрации» — противоречие самому предмету приложения.

Операционализация в Decon:

1. Экран сессии (`views/journal.rs::running_screen`) содержит таймер,
   подсказку и приглушённые кнопки завершения внизу. Никаких
   кнопок-маркеров, хоткеев, всплывающих окон, «отметок срывов» —
   ничего, что требует действия, взгляда или внимания пользователя.
2. Замер состояния — только до и после практики (pre/post-замеры,
   ретроспективные шкалы SCALES.md). Во время сессии в журнал пишутся
   только автоматические события (равномерные `signal`).
3. Обоснование — ARCHITECTURE.md §4.1 (методика дКВ: действия и
   перемещение взора разрушают состояние; психометрия: и probe-caught,
   и self-caught вмешиваются в измеряемый процесс).
4. Зонды дня — вне практики (окно активности, ненормированный день);
   во время живой сессии зонд не всплывает.
5. Изменить это правило можно только отдельным PR с обоснованием
   уровня «новые данные методики», не «удобно для метрик».

## Язык проекта

- Код, идентификаторы, коммиты — английский (международный open source).
- Документация репозитория — русский (язык владельца и первого
  сообщества); перевод на английский — приветствуется, ru-оригинал —
  источник истины.
- UI — ru/en через i18n с первого релиза (заложено в S0: строки не
  хардкодятся, только через слой переводов).
- Шкалы: формулировки локализуются, сопоставимость через `scale_id`
  (SCALES.md §8.4).
